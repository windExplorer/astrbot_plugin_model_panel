## 一、目标 / 非目标

把三件过去混在一起的事拆清楚，各自可配置、可统计、可告警：

| 能力 | 一句话 | 花不花钱 |
| --- | --- | --- |
| **检测**（探测） | 我主动打一次模型，问「你现在通不通、多少毫秒」 | **花**（真实请求） |
| **监测**（观测） | 平时用户对话的耗时/成败，系统自己流过去 | 不花 |
| **配置**（档案） | 每个模型的计费、角色、能力、参与哪些检测 | 不花 |

**非目标**：不改 AstrBot 核心；不写 `provider_stats`（只读）；不做模型回答质量评测；不做多实例分布式协调。

## 二、八个待你拍板的问题

计划阶段最该产出的是这些，实现前需要你定：

1. **`临时免费到期`只做展示，还是进告警？**
   你要求「到期时间选填，只做展示」。但到期后免费转付费是真实踩坑点，接进告警只需在巡检里多一个判断。
   建议：**默认展示 + 到期前 3 天进一次告警队列**，可配开关关掉。要纯展示我按纯展示做。

2. **定时检测的参与名单，要不要由计费类型自动推导默认值？**
   每 10 分钟巡检 50 个模型 ≈ 7200 次真实调用/天。付费模型默认参与会真金白银烧钱。
   建议：`free / temp_free / subscription` 默认可参与，`paid / paid_overage / trial / unknown` 默认**不**参与，用户可逐项覆盖。

3. **真实延迟数据源用哪个？**（决定工作量差别很大）
   - **A 只读 `provider_stats`**：零埋点、零成本，但**漏掉插件内部调用**（`context.llm_generate` / `req_llm`，陪伴插件那几十个后台模型全在内）和第三方 agent。
   - **B 自己埋点**：`on_llm_request` + `on_llm_response` 配对计时，但**失败时响应钩子根本不触发**，失败这一半必须靠 A。
   - 建议：**A 为主 + B 补盲区**，且 B 只在 A 覆盖不到的路径上开。

4. **流式探测要不要做？**
   现在 `provider.test()` 走**非流式** `text_chat`（`provider.py:211-215`），测不到首字延迟，也测不到「只有流式才挂」的网关故障（SSE 断流 / 空 chunk）。
   但流式探测**复用不了 `provider.test()`**，得自己调 `text_chat_stream` 消费到首字再中断 —— 是一个新增子系统的量。

5. **指令的命名与权限？**
   本插件目前**几乎没有指令**（全文只有 `/陪伴分数`，`main.py:571`），加指令是开新范式。
   建议：查询类全员可用（`/模型状态`、`/模型统计`），**检测类限管理员**（花额度，且群里可能被他人乱触发）。

6. **模型档案存新表还是扩展现有 `detection_preferences`？**
   建议**新表 `model_profile`**（档案字段会持续长，且和勾选偏好生命周期不同），检测范围三列另放。细节见第四节。

7. **`provider_stats` 永不清理，我们跟着遭殃吗？**
   核心是 insert-only、无任何 delete/rotation（附录 A.3）。定时检测还会让自己的历史表爆量。
   建议：**原始行不落我们库**（每次按游标增量读核心表），我们只存**聚合快照**（小时/天粒度）+ 短保留期。

8. **版本怎么开？** 这是新功能系列，按 `AGENTS.md` 第三节规则该 `Y` 进位 → **`v1.3.0`**。确认一下。

## 三、核心事实（调研结论，实现前必读）

### 3.1 一个 provider 实例 = 恰好一个模型

`openai_source.py:396-397` 在 init 时 `set_model(provider_config.get("model","unknown"))`，`model` 是**单数**字段；
`get_models()` 返回的列表**不持久化**。切换模型是切**另一个 provider 实例**（核心没有 `/model` 指令，走 `/provider`
→ `ProviderManager.set_provider`，`manager.py:153-219`，按会话写 `provider_perf_chat_completion`）。

> **推论**：本插件语境里「模型」和「provider」是 1:1，**不存在「同一供应商下给不同模型分别定价」的问题**——
> 不同模型本来就是不同 provider。所以档案主键用 `provider_id` 是对的。

### 3.2 计费信息核心完全没有，能力信息核心有

- **计费：彻底不存在。** 全库 grep `pricing/price/cost/currency/billing/free/paid` 无任何配置字段或表列。
  更可惜的一点：models.dev 的 api.json **本身带 cost**，但核心解析时丢掉了 ——
  `LLMMetadata`（`core/utils/llm_metadata.py:19-28`）只留 `id / reasoning / tool_call / knowledge / release_date / modalities / open_weights / limit{context,output}`；
  `openai_source.py:437-447` 的 `get_models()` 更是**只留 `model.id`**。
  → **计费必须我们自己存，无源可自动填。**
- **能力：可以直接白嫖核心。** `LLM_METADATAS`（`llm_metadata.py:30`，由 `update_llm_metadata()` 从
  `https://models.dev/api.json` 拉取）已含上下文窗口、输出上限、是否支持 tool_call、是否 reasoning、模态。
  → **这几个维度不要让用户手填**，读它预填，用户只纠正。

### 3.3 流式是全局开关，不是模型属性

`provider_settings.streaming_response`（`config/default.py:160`）+ `unsupported_streaming_strategy`（`:171`）是**全局**的，
**没有任何 per-provider / per-model 的 `supports_streaming` 标记**。
→ 想知道某个模型流式行不行，要么用户手标，要么**探测**。

### 3.4 现有探测测的是「空载非流式往返」，和真实延迟不可比

`provider.test()` 的 prompt 是 `REPLY \`PONG\` ONLY`（`provider.py:211-215`），**没有 `max_tokens`**，输出极短、输入近零。
真实对话输入几千 token。→ **探测延迟系统性低于真实延迟**，二者**不能放同一个「平均时间」里平均**，也不能互相换算。

### 3.5 失败时，现有 LLM 钩子是瞎的

`OnLLMResponseEvent` 只在 `MainAgentHooks.on_agent_done` 里发（`astr_agent_hooks.py:31`）。
provider 报错时 runner 合成 `LLMResponse(role="err")` 后在 `tool_loop_agent_runner.py:894-910` **直接 return，不调 `on_agent_done`**。
→ 现在记 token 的 `on_llm_response`（`main.py:292`）对失败调用**完全无感**。
且**没有任何 LLM 错误专用钩子**——`OnPluginErrorEvent` 只管插件 handler 异常（`star_request.py:59-66`）。
→ **「报错就告警」只能建立在 `provider_stats.status="error"` 之上**，不能靠钩子。

### 3.6 核心已经在记每次对话的耗时（本方案的地基）

`provider_stats` 表（`core/db/po.py:43-64`）：

| 字段 | 含义 |
| --- | --- |
| `status` | `completed` / `error` / `aborted` ← 就是「调用状态」 |
| `provider_id` / `provider_model` | 归属明确，**不用按模型名反查** |
| `start_time` / `end_time` | float 秒，`time.time()` |
| `time_to_first_token` | 首字延迟，float 秒 |
| `token_input_other` / `token_input_cached` / `token_output` | 用量 |
| `umo` / `conversation_id` | 谁、在哪个会话触发 |

写入：`internal.py:469` 用 `asyncio.create_task` 异步落库，不阻塞回复；`status` 判定在 `internal.py:641-645`。
聚合逻辑核心**已实现过一份**：`dashboard/services/stat_service.py:304-388`（平均耗时、平均 TTFT、成功数）。
读取通道：`self.context.get_db()`（`context.py:777`）→ `async with db.get_db() as session: select(ProviderStat)`。

**盲区（必须知道，否则统计口径会骗人）**：

1. **插件内部调用不进表**：`context.llm_generate`（`context.py:171`）/ `context.tool_loop_agent` / 插件里的 `req_llm` 都不经过 `internal.py:470` 那个写入点。陪伴插件后台几十个模型全漏。
2. **第三方 agent 不记**（dify / coze / dashscope / deerflow，`third_party.py:399-405` 无落库）。
3. **粒度是「一轮对话」不是「一次 HTTP 调用」**：`start_time` 在 `reset()` 里只设一次（`tool_loop_agent_runner.py:326`），agent loop（`astr_agent_run_util.py:133`）里多轮工具调用耗时被合并 → `end_time - start_time` **含工具执行时间**。
4. **`time.time()` 非单调时钟**，系统校时会产生异常值。
5. **`provider_stats` 永不清理**（附录 A.3）。

### 3.7 provider_id 可改可删，且核心不做级联清理

`delete_provider`（`manager.py:910-932`）与 `terminate_provider`（`:880-908`）只删配置项、终止实例、`del inst_map[id]`，
**不碰任何依赖数据**。且 `id` 用户可编辑（`update_provider` 整条替换，`manager.py:947-956`）。
→ **我们库里所有以 `provider_id` 为键的表都会产生孤儿行，必须自己做回收。**

### 3.8 告警通道现成，且工作区已有可抄实现

`context.send_message(umo, chain)`（`context.py:614`）官方支持无事件主动投递，适配器侧明确 `event=None`
（`aiocqhttp_platform_adapter.py:109-126`）。
**直接复用**：`astrbot_plugin_user_gateway/main.py:1679-1703` 的 `_notify_admins`（读 `admins_id` 拼 `{platform_id}:FriendMessage:{uid}`，逐条 try/except）。

## 四、数据模型：模型档案

### 4.1 维度拆分原则

你说的是「付费分类」，但**别把来源、角色、计费塞进同一个枚举**——那样会出现「本地部署的付费模型」「中转站的订阅」这类无法表达的混合态。拆成**四个正交维度**：

- `billing_type` 计费方式（钱怎么花）
- `channel_kind` 来源渠道（钱付给谁 / 靠不靠得住）
- `role` 角色定位（在我们体系里干什么）
- 能力组（读核心 `LLM_METADATAS` 预填，不手填）

### 4.2 `billing_type` 计费分类（含你要的其他类型）

| key | 中文 | 判定标准 | 附加字段 | 默认定时检测 |
| --- | --- | --- | --- | --- |
| `unknown` | 未标注 | 默认值，面板灰显 | — | 否 |
| `free` | 长期免费 | 官方明确长期免费（含本地部署、自建） | — | **是** |
| `temp_free` | 限时免费 | 官方公告期免费 | `free_until`（**选填，仅展示**） | **是** |
| `trial` | 试用赠送 | 一次性送额度/送天数，用完即停 | `trial_quota` | 否 |
| `paid_overage` | 额度+超额付费 | 有免费额度，超出计费（最常见也最易翻车） | 额度值 + 单价 | 否 |
| `paid` | 按量付费 | 纯 token 计费 | 单价 + 币种 | 否 |
| `subscription` | 订阅内含 | 包月套餐已付，单次调用无边际成本 | 续费日 | **是** |

> `paid_overage` 值得单列：它平时表现为「免费」，额度用完后**同一天内从绿变红**，是最容易被漏掉的预算炸弹。

**价格明细（仅 `paid` / `paid_overage` 需要填）**：

| 字段 | 说明 |
| --- | --- |
| `currency` | `CNY` / `USD` |
| `price_input_per_m` | 输入单价，**每百万 token** |
| `price_output_per_m` | 输出单价 |
| `price_cached_per_m` | 缓存命中单价（DeepSeek 类缓存折扣很大，不填会明显高估） |

> **单价统一「每百万 token」**，因为不同站混用 `/1K`、`/1M`，不锁死单位后面成本估算必错。

**由此白送的实用功能**：核心已有 token 用量（`provider_stats` 三列 + 我们自己的 `llm_usage` 表已含 `cached_tokens`），
配上单价就能算 **`本月预估花费`**：

```
成本 ≈ (input_other × 输入价) + (input_cached × 缓存价) + (output × 输出价)
```

这是付费分类唯一能自动兑现成决策价值的地方（「这个模型其实一个月花 47 块，值不值得留」）。

### 4.3 `channel_kind` 来源渠道

`official`（官方直连）/ `aggregator`（聚合站，OpenRouter 类）/ `reseller`（国内中转，**注意跑路风险**）/ `self_hosted`（本地 Ollama / vLLM / LMStudio）/ `unknown`

> 作用不是好看的标签：它决定**告警口径**（中转站 502 频发是常态，阈值应比官方宽松）
> 和**成本语义**（`self_hosted` 成本为 0 但吃硬件，`aggregator` 可能偷偷降级模型）。

### 4.4 `role` 角色定位

`primary`（主力，正在给用户们服务）/ `backup`（备用）/ `fallback`（兜底降级链）/ `dedicated`（某插件专用）/ `watch`（观察中）/ `retired`（已弃用但仍配置着）

> `primary` 有特权：出问题时告警**优先级最高**，且面板上要和普通模型区分——
> 主力模型标红和观察模型标红，你的反应完全不同。
> 注意 AstrBot 全局默认模型可只读拿到（`main.py` 已有 `api_default_model`），**`primary` 应自动包含它**。

### 4.5 能力组（读核心预填，不要求手填）

来自 `LLM_METADATAS`（`llm_metadata.py:30`）：`context_limit` / `output_limit` / `tool_call` / `reasoning` / `modalities` / `open_weights`。
插件侧**只做纠正**（模型名不在库里时留空）。

**必须我们自己标的两个**：

- `supports_streaming`：`true` / `false` / `unknown` —— 核心无此字段（见 3.3）。
- `probe_mode`：`non_stream` / `stream` / `both` —— 决定探测走哪条路（见第五节）。

### 4.6 检测范围：三通道各自独立（你这条需求的落地形态）

三个通道**回答的是三个不同的问题**，所以必须是三个独立开关，不能合并成一个 `enabled`：

| 通道 | 回答的问题 | 现有 | 目标 |
| --- | --- | --- | --- |
| `allow_manual` | WebUI 一键/分组检测，**我手点的** | ✅ `detection_preferences.enabled` | 沿用 |
| `allow_scheduled` | **系统自己花我的钱**去巡检 | ❌ | 新增 |
| `allow_command` | **谁能点、能点哪些**（群里他人可触发） | ❌ | 新增 |

> 现有 `enabled` 语义正是 `allow_manual`，**保持不动做向后兼容**，新加两列。
> 建议新表 `model_profile` 承载档案，`detection_preferences` 只加 `allow_scheduled` / `allow_command` 两列。

**默认值规则**（呼应第二节问题 2）：`allow_scheduled` 的默认由 `billing_type` 推导，而不是让用户逐个点开 50 个模型。

### 4.7 表结构草案

```sql
-- 模型档案：一行一个 provider，字段会持续长
CREATE TABLE IF NOT EXISTS model_profile (
    provider_id      TEXT PRIMARY KEY,
    billing_type     TEXT NOT NULL DEFAULT 'unknown',
    free_until       INTEGER,               -- 可空，仅展示；秒级时间戳
    currency         TEXT NOT NULL DEFAULT '',
    price_input_per_m  REAL,
    price_output_per_m REAL,
    price_cached_per_m REAL,
    channel_kind     TEXT NOT NULL DEFAULT 'unknown',
    role             TEXT NOT NULL DEFAULT 'unknown',
    supports_streaming TEXT NOT NULL DEFAULT 'unknown',  -- true/false/unknown
    probe_mode       TEXT NOT NULL DEFAULT 'non_stream',
    note             TEXT NOT NULL DEFAULT '',
    model_name       TEXT NOT NULL DEFAULT '',  -- 快照，供 provider 删除后回显
    updated_at       INTEGER NOT NULL
);

-- 健康快照：派生指标 + 告警状态机的宿主
CREATE TABLE IF NOT EXISTS model_health (
    provider_id      TEXT NOT NULL,
    window_start     INTEGER NOT NULL,       -- 聚合窗口左界
    window_sec       INTEGER NOT NULL,       -- 窗口长度
    source           TEXT NOT NULL,          -- probe / live
    total            INTEGER NOT NULL DEFAULT 0,
    ok_count         INTEGER NOT NULL DEFAULT 0,
    fail_count       INTEGER NOT NULL DEFAULT 0,
    avg_latency_ms   REAL,
    p95_latency_ms   REAL,
    avg_ttft_ms      REAL,
    last_error_code  TEXT NOT NULL DEFAULT '',
    state            TEXT NOT NULL,          -- unknown/healthy/degraded/down/muted/disabled
    consecutive_fail INTEGER NOT NULL DEFAULT 0,
    est_cost_milli   INTEGER NOT NULL DEFAULT 0,  -- 窗口内估算成本，厘(1/1000元)
    PRIMARY KEY (provider_id, window_start, source)
);

-- 告警事件：可追溯、防刷屏
CREATE TABLE IF NOT EXISTS alert_events (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    provider_id      TEXT NOT NULL,
    kind             TEXT NOT NULL,          -- fail_burst / recovered / free_expiring / slow
    state            TEXT NOT NULL,          -- open / notified / resolved
    detail           TEXT NOT NULL DEFAULT '',   -- 已脱敏
    opened_at        INTEGER NOT NULL,
    notified_at      INTEGER,
    cooldown_until   INTEGER
);
```

> `est_cost_milli` 用整数厘存，避免浮点累加误差；`model_profile` 用 REAL 存单价没问题。

## 五、测量口径：四种延迟，永远分开显示

**这是整个方案最容易做错、也最容易骗自己的地方。** 所有 UI 文案、指令输出、导出字段都必须带口径后缀，禁止出现一个笼统的「平均延迟」。

| 代号 | 名称 | 来源 | 语义 | 坑 |
| --- | --- | --- | --- | --- |
| **D1** | 探测延迟 | `model_test_results.latency_ms`（`main.py:2048-2051`，单调时钟） | 空载非流式往返 + 一次 PONG | 系统性低于真实值（3.4） |
| **D2** | 首字延迟 TTFT | `provider_stats.time_to_first_token` | 用户体感「卡不卡」← **最该展示的** | **仅流式路径有值**（`tool_loop_agent_runner.py:832`），非流式恒为 0 |
| **D3** | 整轮耗时 | `provider_stats.end_time - start_time` | 「这轮回复让我等了多久」 | **含工具执行、含多步 agent 循环**（3.6.3） |
| **D4** | 流式探测延迟 | 新增流式探测（若做） | 流式路径的可用性 + 首字 | 需新写探测路径，不能复用 `provider.test()` |

**D2 的 `TTFT = 0` 二义性**必须在读侧判别：结合 `token_output > 0` 与是否有流式标记，区分「快」和「没测到」，
否则「平均 TTFT」会被一堆 0 拉低到失真。**这是实现时的硬性要求，不是 nice-to-have。**

**展示策略**：

- 「模型有多快」→ 主展示 **D2**，副展示 D3 且改名叫「本轮耗时」不叫「模型延迟」。
- 「模型通不通」→ 展示 **D1**，并标最后一次探测时间。
- 两者永不混算。

## 六、监测与告警

### 6.1 健康状态机（五态 + 一个禁用）

`provider_stats` 只有二值 `status`，直接拿来告警会很钝。需要显式状态机：

```
unknown ──首次探测成功──> healthy
healthy ──连续 N 次失败────────> down
healthy ──成功但 p95 超阈值────> degraded
degraded ──回到基线内──────────> healthy
down ──连续 M 次成功──────────> healthy   （恢复通知）
任意状态 ──用户手动静默────────> muted     （不参与告警）
用户关闭全部通道 ─────────────> disabled   （不参与任何检测）
```

> `degraded` 是必需的：**超时和慢常常是高峰期过载而非故障**，只有二值会把健康模型判死，进而做出错误决策。
> `muted` 也是必需的——某个模型你明知它坏了且正在等供应商修，需要关掉噪音而不是删配置。

### 6.2 告警规则

| 规则 | 建议默认 | 为什么必须有 |
| --- | --- | --- |
| 连续失败阈值 | 3 次（探测）/ 5 分钟窗口内 ≥3（实时） | 单次失败多半是抖动 |
| **冷却窗口** | 同 `(provider_id, kind)` 30 分钟内不重复 | **没有它就会刷屏**：一个坏模型按每条对话的频率刷 |
| 恢复通知 | 开 | 只有告警没有恢复，管理员永远不知道修好没 |
| 供应商级聚合 | 同 `channel_kind` + 同 `api_base` 且 ≥3 个模型同时 down → 合并成 1 条 | 一家挂 10 个模型时，10 条告警不如 1 条有用 |
| 基线偏离 | p95 > 自身 7 日基线 × 2（且样本 ≥20）→ `degraded` | 固定阈值对慢模型天天报、对快模型失灵 |
| 冷启动保护 | 样本 < 20 不判 `degraded` | 低频模型「平均延迟」本就无统计意义 |
| `rate_limit` 特殊处理 | **不计入失败**，单独一类「受限」 | 并发检测和真实高负载都会自己触发 429，把健康模型判死 |
| 限时免费到期 | 到期前 3 天一次（若第二节问题 1 选了进告警） | 免费转付费是真实预算事故 |

**判定口径**：`error_code` 沿用现有归一化（`main.py:117-138`：`timeout / refused / connect / auth / rate_limit / not_found / server / unknown`），**不要另造一套**。

### 6.3 告警投递

- 通道：`context.send_message()` + 复用 `user_gateway` 的 `_notify_admins` 形态（3.8）。
- **`event.send` 禁用**：`cosyvoice/main.py:695-697` 记着教训——它只往结果链追加、**不抛错**、事件结束后静默丢弃。
- **自循环防护**：主动发的消息会重新进 pipeline（`cosyvoice/main.py:300-301`）。告警文本若被自己的钩子当成对话又触发一次 LLM 调用，可能滚起来 → 按内容特征去重。
- **必须脱敏**：`_normalize_error` 的 80 字符截断**不保证不含 `api_key` / 内部 `base_url`**（异常字符串可能回显请求信息）。发送前显式 redact 密钥串与 URL 的 query 部分。

### 6.4 调度

两条路，建议**用 A**：

- **A**：`initialize()` 里 `asyncio.create_task` + `terminate()` 里 cancel —— `user_gateway/main.py:308-336` 是工作区已验证的写法。注意 `Context.register_task` **已废弃**（`context.py:881`）。
- **B**：`context.cron_manager.add_basic_job(...)`（`core/cron/manager.py:148`，`persistent=True` 可跨重启）。语义更正规，但重启后残留 job 需自己管生命周期。

> `terminate()` 只有**在类里直接定义**才会被调用（`star_manager.py:1962`，查 `__dict__`，继承来的不算）。
> 漏定义 = 热更后旧任务继续跑，**同一份巡检双份执行**。这是必踩坑。

## 八、你可能没想到、但会咬人的东西

按「不处理会怎样」排序：

1. **成本失控（最伤）**：探测未设 `max_tokens`（`provider.py:211-215`），付费模型重试一次 = 双倍花钱。
   → 探测请求要限 `max_tokens`；**`paid` 类模型重试次数单独配，建议默认 0**；定时巡检要有**每日调用预算上限**。
2. **并发检测自触发 429**：并发一高，健康模型被判故障。→ 并发上限 + `rate_limit` 不计失败（6.2）。
3. **数据量爆炸**：`provider_stats` 核心永不清理；定时巡检每 10 分钟 × 50 模型 ≈ 7200 行/天。
   → 原始行**不进我们库**，只存聚合快照 + 短保留期（探测明细留 7~30 天）。
4. **孤儿行**：`provider_id` 可被用户改名/删除，核心不做级联清理（3.7）。
   → 巡检任务里加一次回收（`model_profile` / `model_health` / `detection_preferences` 里 provider 已不存在的行，标记后清理）。
5. **`degraded` 缺失导致误判**：二值状态把高峰期慢判成故障。见 6.1。
6. **样本不足骗人**：低频模型一周 3 次调用，「平均延迟 1200ms」毫无意义。→ 展示必须带 `n=`，样本少时标灰不给结论。
7. **D1 与 D2/D3 混算**：一个笼统「平均时间」。→ 第五节口径写死进文案。
8. **白送的能力元数据没利用**：`LLM_METADATAS` 已在内存里（`llm_metadata.py:30`），
   上下文窗口 / tool_call / reasoning 全都现成，不要让用户手抄。
9. **计费无源可填**：核心丢掉了 models.dev 的 cost（3.2）。→ 一期只做手动填；
   若以后要预填，需插件**自己**发一次 `https://models.dev/api.json`（多一个外部依赖 + 网络失败要兜底，建议二期再说）。
10. **默认模型保护**：全局默认模型被标红时，视觉要区别于普通模型（它是「正在服务用户的那个」）。
11. **时区与跨天边界**：`llm_usage.day` 是本地日期，`provider_stats.created_at` 是 UTC（核心聚合特意做了转换 `stat_service.py:304-313`）。
    → 我们聚合必须同样按本地时区切，否则「今日成本」在早晚各错一次。
12. **AstrBot 升级静默失效**：读 `provider_stats` 是伸手进核心内部表，而 `metadata.yaml` 声明的是 `astrbot_version: ">=4.22.0"`
    —— 4.22 未必有这张表。→ 读取封成**单文件只读适配层**，字段全 `getattr` 兜底，读不到就降级只用自己的探测数据并在面板说明「监测不可用」，**绝不异常上抛**。
13. **工作区硬约束**（`AGENTS.md`）：
    - 新增顶层模块必须**同时**进 `build_zip.ps1` 的 `$includeList` **和** `main.py` 的 `importlib.reload` 热重载列表；
    - 新增配置键必须**三处同步**：`_conf_schema.json` / WebUI 分区表 / i18n 四语言（zh/en/ja/ko，key 用嵌套结构）；
    - 本仓库版本由 `_bump_version.ps1` 自动 bump，但开新功能系列要手动把 metadata 改成新 `Y`（`v1.3.0`）。

## 九、分期

依赖关系是单向的，**M1 独立可做**，后面每期都能单独交付。

| 期 | 状态 | 内容 | 产出价值 | 依赖 |
| --- | --- | --- | --- | --- |
| **M0 档案层** | ✅ 后端完成，缺档案页 | `model_profile` 表 + 计费/渠道/角色/三通道配置 + 能力预填 + 孤儿回收 | 配置类需求一次性闭环，后面全靠它 | — |
| **M1 监测层** | ✅ 后端+指令完成 | `stats_reader` 只读适配层 + 健康态判定 + `/模型状态` `/模型统计` 卡片 | **零埋点零成本，最快见效** | 弱依赖 M0 |
| **M2 告警层** | ✅ 完成 | `model_state` 状态机 + `alert_events` + 冷却/合并/恢复/静音 + 巡检任务 + 管理员投递 | 出事自动告诉我 | M0 + M1 |
| **M3 定时探测** | ⬜ 未做 | 按 `allow_scheduled` 的巡检 + 并发上限 + 预算护栏 + 成本控制 | 主动发现，不靠用户撞 | M0 + M2 |
| **M4 流式探测** | ⬜ 未做 | `probe_mode` 生效 + 流式探测路径 + D4 口径 | 补齐「只有流式才挂」的盲区 | M3 |
| **M5 指令检测** | ⬜ 未做 | `/检测模型` + 限管理员 + 异步回执 | 补齐入口 | M0 + M3 |

> **实现期补的口径修正（原文档没写到）**：
> 1. `aborted` 既不算成功也不进失败率分母；恢复需连续成功 2 次，且恢复通知同样受冷却约束。
> 2. 投递失败必须可重试——若状态在投递前就落成 `down`，下一轮 `before==down` 不再触发，
>    「管理员还没配好」时的第一条告警会被永久吞掉。现在未送达事件保持 `open` 且
>    `notified_at` 为空，由下一轮补发，超 24 小时放弃。
> 3. 告警文案必须显式脱敏，且**脱敏规则顺序有讲究**：通用 `key=value` 若先跑，
>    会把 `Authorization: Bearer xxx` 里的 `Bearer` 一词吃掉，令牌值反而逃过脱敏。
> 4. 首轮巡检把游标放到表尾跳过历史，否则装上第一秒就会因陈年失败发莫名告警。
> 5. 多模型故障合并成一条卡片；`/模型静音` 只关通知不关采集。

> **建议 M1 先做**：它不写核心表、不花额度、不改探测链路，能立刻回答「我的模型平时到底多慢、最近错了几次」，
> 而且会**用真实数据验证第五节的口径假设**——很可能看完数据你就改主意了。
> M3（定时探测）是这套方案里**唯一持续烧钱**的部分，值得等有数据支撑再开。

## 十、建议砍掉的（防Scope膨胀）

- ❌ 模型回答质量评测（需要评测集与判分模型，另一个项目）
- ❌ 自动切换默认模型 / 故障自动降级链（风险高，AstrBot 侧语义复杂）
- ❌ 多用户各自看自己模型的数据（这是单管理员面板）
- ❌ 一期做 models.dev 成本预填（外部网络依赖，手填更快落地）
- ❌ 把 `provider_stats` 搬进我们自己的库（核心表会自己长大，重复存等于双倍）
